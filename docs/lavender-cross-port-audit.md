# Lavender cross-port reuse audit

**Scope:** compare the pinned Lavender bring-up against other local Portsmith ports/components for possible design reuse. This is source/document inspection only. No code was copied, no submodule initialized, no build/device operation was performed.

- **Portsmith checkout:** `ports/lavender/repo` at `1462374c61308e9b6dce0bb6a3fd7dc0add08fb9` (`UniXNU-Lavender`). Root license declares BSD-2-Clause-Patent; keep the component/vendor terms separate.
- **Target:** Xiaomi Redmi Note 7 (`lavender`), Qualcomm SDM660; 4 GiB DRAM; SK Hynix 128 GB eMMC using `qcom,sdhci-msm-v5` at the phone-recorded `0xc0c4000`; Xiaomi ABL; custom EDK2 derived from this phone's XBL; PSCI over SMC; NT36672A display and Novatek touch. These are target-specific facts in the pinned README/board configuration, not transferable defaults.

## Current Lavender evidence boundary

The pinned README reports that custom firmware and the UniXNU menu/fixture reached a 5/5 fixture result on device. It explicitly leaves the Lavender XNU board milestone, native eMMC, display/touch and full iOS userland work incomplete. The panic-recovery notes record host contract tests and an authorized historical payload flash, but do **not** qualify panic recovery: a later recovery read found a valid `ring.loc` but no `bootlog.txt`, and the owner recalled a missing ring magic status. DRAM retention through SMC → monitor → ABL → UEFI remains unknown. The current recovery follow-up build was not deployed after the phone disappeared from ADB/fastboot. See [`ports/lavender/AGENTS.md`](../ports/lavender/AGENTS.md), `ports/lavender/repo/README.md`, and `docs/panic-recovery-status.md` at the pinned source.

One local configuration question remains before relying on the RAM-root fallback: the README says a RAM block root carries bring-up until eMMC is ready, while the pinned `configs/lavender_defconfig` sets `CONFIG_XNU_NATIVE_RAM_BLOCK=n`. Resolve the actual boot profile/selection before using this as a baseline.

## Practical next steps (no code transplant proposed)

1. Keep the SDM660 SDHCI/eMMC implementation in `ports/lavender/repo`; use Sirius only to compare the block-device boundary and host/device test structure. First document the exact SDM660 controller/clock/voltage/DMA contract from Lavender's pinned FDT and attributable upstream sources.
2. Resolve whether `RamBlock` is enabled in the actual Lavender build profile before relying on it. Keep a RAM-root smoke test separate from persistent eMMC qualification.
3. For the panic ring, use the existing local host tests and ESP reader. Do not infer DRAM retention from `ring.loc`; recovery/archive behavior remains unverified and any new device state transition needs current authorization.
4. For touch/display, compare exact controller part numbers, buses, firmware and frame memory against the Lavender source before borrowing even protocol-level code. Similar “Novatek” naming is not enough.
5. Keep candidate code in its own pinned source for now. Any later import needs a file-level license/provenance review, host tests and a separate Lavender-specific adaptation record. No code was copied during this audit.
